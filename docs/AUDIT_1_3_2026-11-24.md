# RUDRA 1.3.0 audit: security, robustness, performance, UI (24 Nov 2026)

Read-only review of what ships, done while the learned-route GPU run went on (no build, no test run, no
change). Every finding below was checked against the code at the line given. Severity: High, Medium, Low.
Nothing Critical or High was found: the security review of 11 Nov 2026 had already closed the big holes.

**Status, 24 Nov 2026 about 01:50 Cairo:** 2, 3, 4 and 5 are fixed in the working tree, and a Deliver menu for
the EXR compression (ZIP, ZIPS, None) answers part of 12. Written but **not built or tested yet**: the build
and `scripts\NATIVE_TESTS.ps1 -Filter "Process*:Exr*:OutputSize*:AppDeliver*:AppBatch*:Batch*"` come next.
Item 17 was found while doing them. 1 needs a GPU check after the night's runs; 6-16 are for later.

## What was checked and holds

- **Model downloads** (`model_downloads.cpp`): https only, every file's SHA-256 compiled into the app
  (`is_known_model_file`), relative paths with no `.`/`..` (`safe_relative`), no less safe redirects, a file
  renamed into place only after its size and hash check.
- **Update check** (`project_tab.cpp:300`): it only says so; an address is opened only when it is https.
- **Process launches**: the native launcher resolves full paths and refuses `.bat` (`platform/src/process.cpp`);
  PowerShell is started from System32 by full path; the Python fill runs with the app's own python folder as
  its working folder (`genfill_job.cpp:606`), so nothing in a user folder is imported.
- **Unsafe loading**: `torch.load(..., weights_only=True)` everywhere; Florence-2 through transformers' own
  class (no `trust_remote_code`); the Wan base downloaded at a pinned revision and checked file by file.
- **Parsers of untrusted files**: the EXR reader bounds every read (`deliver/src/exr.cpp:460`); the PNG/ICC
  reader's inflate has an output limit (`media/src/still_metadata.cpp:83`); every `nlohmann::json::parse` that
  reads a file is inside a try; the QC report escapes every name and value it writes (`qc_report.cpp:27`).
- **Supply chain**: package dependencies pinned by hash (FFmpeg 8.1.2, OpenCV 4.14.0, ONNX Runtime 1.24.4,
  OCIO 2.5.2, uv 0.13.7), GitHub Actions pinned to commits, pip-audit and CodeQL (Python) weekly.
- **No network listener** in the app; **no secrets** in the source, scripts, tools, configs or workflows.
- **Playback** already avoids redrawing the whole UI every frame (`main_window.cpp:1313`, 1367).

## Findings

### Before 1.3.0 (small, low risk)

| # | Sev. | Area | Finding | Fix |
|---|---|---|---|---|
| 1 | Medium | AI fill, reproducibility | What users get is not what v5 was tested in. "Set up automatically" installs `scripts/genfill_constraints.txt` (diffusers 0.41.0, accelerate 1.15.0, openexr 3.5.2) and the newest PyTorch on the cu128 index (unpinned); every v5 check ran in the PC's `.venv`: diffusers 0.39.0, accelerate 1.14.0, openexr 3.4.13, torch 2.13.0+cu130. The file's header says its top-level versions are the development environment's; they are not any more. | Either bring `.venv` to the constraints (`uv pip install -c scripts\genfill_constraints.txt ...`) and run one short v5 check (Porch, about 15 min of GPU) against tonight's numbers, or pin the constraints to the tested versions (keeping accelerate 1.15.0, which closes PYSEC-2026-3804). Give PyTorch a range in both bootstrap scripts (for example `torch>=2.6,<2.14`): 2.6 is also the floor for CVE-2025-32434. |
| 2 | Medium | Security | Two programs are started by bare name through QProcess: `ffprobe` (`main_window.cpp:3206`, `movie_is_lossy`) and `nvidia-smi` (`genfill_job.cpp:455`, the AI fill pre-flight). Windows' CreateProcess looks in the current folder before System32 and the PATH: the reason the 11 Nov review made the native launcher resolve full paths. A folder holding its own `ffprobe.exe` or `nvidia-smi.exe` could have it run. | Resolve both with `QStandardPaths::findExecutable` (as `edl.cpp:84` does); `nvidia-smi` also from System32. **Done:** both resolved with `findExecutable`; nvidia-smi falls back to `%SystemRoot%\System32\nvidia-smi.exe`; not found means not run. |
| 3 | Medium | Performance (new in 1.3) | The Batch tab reads each still's or sequence's first frame for its thumbnail on the UI thread (`batch_page.cpp`, `thumb_for`): a queue of many large stills freezes the window when the tab is first shown. | Decode on a worker thread (as the media scans do) and set the icons when they arrive. **Done:** decoded on `QThreadPool`, set when they arrive (each file once; a closed tab drops the result). |
| 4 | Medium | Robustness (new in 1.3) | Output size 2x has no ceiling (`core/src/resample.cpp:21`): a 6K or 8K source asks for 12K-16K frames, about 1.6 GB a float frame, past HEVC's 8192x4320; it fails late or runs out of memory. | Grey out 2x (and refuse it in the request) when the result would be wider than 8192, with the reason in its tooltip. **Done:** `kMaxOutputSide = 8192` in `resample.hpp`; a size past it is greyed with the reason, the request falls back to the source size, and `output_size` itself never returns more (test `OutputSize.NoSideIsWrittenPast8192`). |
| 5 | Medium | Robustness | Children outlive a crash: no Windows Job Object anywhere. If RUDRA crashes or is ended from Task Manager, the AI fill (about 16 GB of VRAM), the learned engine and ffmpeg keep running; the next start finds the GPU busy. | At start, put RUDRA in a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (about 20 lines in `main.cpp`, Windows only); every child then ends with it. **Done, differently:** the children join a kill-on-close job that RUDRA holds (the platform `Process` for ffmpeg and ffprobe; the QProcess children through `child_process.hpp`), not RUDRA itself, so a program it opens for the user (a folder, an installer) is not ended with it. Test `Process.AChildEndsWithThisProgram`. |
